# LAN IM Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development to implement and review each task.

**Goal:** Deliver an operational DBX + browser LAN messenger with invitation accounts, conversations, attachments and trusted peer nodes.
**Architecture:** Isolated backend/im package serves authenticated HTTP and exposes same API through im/request RPC for DBX sandbox. Shared static UI packaged into ui/ and embedded for browser serving. Node discovery and federation use stable signing keys.
**Tech Stack:** Go standard library, vanilla JS/CSS, existing DBX Go SDK.
**Spec:** docs/superpowers/specs/2026-11-10-lan-im-design.md

## Global Constraints
- Keep plugin ID io.github.yuzhi.localsend; version 0.2.0.
- Preserve legacy channels and files; new data in plugin data directory im/.
- Never expose password hashes, invite tokens, node private keys or session tokens in public lists.
- No native alert/confirm/prompt; UI theme tokens and responsive layouts.

## API contract
All authenticated calls carry Authorization: Bearer TOKEN. HTTP errors JSON {error:string}; success JSON objects. DBX RPC im/request params {method,path,token,body} returns {status,body}; body JSON object. Browser uses /api/im prefix. Lists use {users:[]}, {conversations:[]}, {messages:[]}. User {id,username,nickname,bio,avatar,admin,disabled,lastSeen}; conversation {id,name,kind,members:[],updatedAt}; message {id,conversationId,senderId,text,attachmentId,createdAt}; attachment {id,name,size,mime,sha256}. Client supplies message id for idempotence.

## Implementation decisions
- Work stays on codex/lan-im in the existing checkout; no merge or publish.
- Direct identity is node-wide, accessible only to local DBX admin. Ordinary web accounts cannot inherit host trust or read its direct messages. Per-person distributed keys would require a separate protocol.
- Keep legacy data and source but do not expose legacy UI through new service or auto-start old unauthenticated HTTP endpoints.
- Local JSON state targets small teams and one process per data directory. No claim of E2E encryption or enterprise scale.
- Candidate package script includes only new UI runtime assets, correcting old documentation that omitted external JS/CSS. Formal store release still requires official CLI validation/signing workflow.
